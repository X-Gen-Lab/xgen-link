# Datalink 接收与资源优化

本轮基于 `d7bbb75` 完善接收恢复、栈使用及内部接口。wire v3、公开结构 ABI、profile ID 和五个独立基础组件依赖保持。以下数据来自固定 Cortex-M0 探针，不能代替产品固件或板级测量。

## 完成的改动

| 范围 | 结果 |
| --- | --- |
| 候选帧超时 | 重叠 magic 替换候选时刷新起点，后续头/载荷不延长绝对期限 |
| 超容量帧 | 基础头完成即拒绝明显超容量候选；扩展完成后检查认证标签开销 |
| parser 热路径 | view 参数要求非空；兼容字节入口自行提供临时 view |
| parser 状态 | 删除重复 CRC 索引，头长度使用 8 位字段，保留真实缓存进度与时间 |
| 接收结构 | 合并 metadata 包装，raw 与 stream 共用 wire 状态分类；poll 调用同步 span 入口 |
| 层间接口 | packet/frame 各自分为 TX/RX 单向端点，实例静态绑定 |
| 读取块 | 构建时选择实际容量，安装头与预算报告共同记录它 |

span 入口内部仍逐字节推进 parser。它让组帧、同步交付与错误恢复只有一个入口，不代表 DMA 异步支持、批量解析性能提升或零拷贝接收。完整 view 只在同步调用期间借用 cache；上层 BUSY 后仍继续消费余下输入，并返回首个交付错误。

## Cortex-M0 完整镜像

工具链为 Arm GNU 15.2.rel1 / GCC 15.2.1，`-Os`，Boot、单 peer、单路由、单 link、窗口 1。RX cache 与 MTU 相同；额外栈预留始终为 1,024 B。

| MTU/RX | LTO | 本轮读取块 | Flash | workspace | 静态 RAM | 含预留栈 RAM | 最大单函数栈 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 128 | 关闭 | 32 B | 15,988 B | 1,112 B | 1,176 B | 2,200 B | 192 B |
| 64 | 关闭 | 32 B | 15,988 B | 920 B | 984 B | 2,008 B | 192 B |
| 128 | 开启 | 32 B | 12,600 B | 1,112 B | 1,176 B | 2,200 B | 224 B |
| 64 | 开启 | 32 B | 12,600 B | 920 B | 984 B | 2,008 B | 224 B |

前一轮读取块为 128 B：普通构建 Flash 为 15,932 B、最大单函数栈 272 B；LTO 为 12,600 B、312 B。本轮普通 Flash **增加 56 B**，LTO 不变；两种 MTU 的 workspace、静态 RAM、总 RAM 各减少 **24 B**。栈变化同时包含严格 view、span 分层与读取块缩小的影响，不能全部归因于算法优化。

32 位目标的 parser **32→24 B**，每 PHY link **48→40 B**；四个端点合计 **48→32 B**。因此单 link 配置共减少 24 B 常驻工作区。原 metadata 包装不在该 Boot ELF 中，删除它不计作 Boot Flash 节省；普通构建实际链接的 datalink 符号反而从 1,290 B 增为 1,366 B，其他层和对齐变化也计入上述完整镜像。

## 栈数据怎样解释

非 LTO 的 `feed_byte_view` 单函数静态栈 **104→40 B**。旧兼容 `feed_byte` 的局部 view 被移到包装自身，不能声称该兼容路径也节省同样空间。

新的 `poll_parser` 为 **80 B**，它调用的 `consume_span` 为 **136 B**，还会进一步调用 parser、wire 和上层。不能把 80 B 当作全部接收栈。表中的 192/224 B 是完整 ELF 中最大的已链接单函数静态值；1,024 B 只是预留，均不证明调用链、回调或 ISR 嵌套峰值已验收。

## 产品如何选择读取块

配置库时指定 `-DXGL_DATALINK_RX_CHUNK_SIZE=AUTO|16|32|64|128`。AUTO 在 Boot 选 32，其余 profile 选 128。选择较小值不改变 MTU、RX cache 或 wire 能力。消费已安装库时不能通过冲突的预处理宏改变它。

每条到期链路每次 step 只读取一次，读取量为运行期字节预算与 chunk 的较小值。读取 128 字节完整帧在 chunk32 下至少需要四次满读取；驱动短读会增加次数。产品必须联合设计驱动 ring 容量、轮询频率和整帧期限。每毫秒读取 32 字节的理想持续上限是 32,000 B/s，还需预留突发和调度余量。

资源报告的 `rx_chunk_bytes` 来自目标编译的布局探针。预算同时核对实际 chunk、MTU/RX、profile 与 LTO；旧报告缺少 chunk 不能用于本轮限额。历史基线仍标明 chunk128，不把两种工作量配置伪装成相同条件。

## 验证与边界

新增测试覆盖候选替换与回绕、绝对超时、超容量后的正常帧、认证 trailer、双 CRC、所有 span 拆分位置、多帧尾部、错误恢复、BUSY 后继续及输入借用。构建契约覆盖 AUTO 切换、安装头、非法值和宏冲突。完整主机、sanitizer、覆盖率及 ARM 结果见仓库 `design/validation/datalink-optimization.md`，设计决策见 `design/adr/0008-datalink-runtime.md`。

探针无堆服务或未解析符号。它不包含真实 BSP、DMA、Flash 写入、看门狗、升级业务和生产密码 provider。两种构建均未达到 8 KiB Flash 目标；MTU64 的 workspace 小于 1 KiB。远端 CI、发布和板级验收分别确认。
